# 시나리오 · 공정 N빵 계산기

시나리오는 세 묶음입니다.

- **A. 계산 규칙 시나리오**: 지금 만든 `computeSplit()`이 맞게 나누는지 확인합니다. `tests/test_scenarios.js`로 자동 검사합니다.
- **B. 멀티 에이전트 시나리오**: 다음 단계에서 Agent를 붙였을 때 확인할 흐름입니다. 계획서 7장의 "정상 · 부분 실패 · 전체 실패 · 승인 거부" 기준에 맞췄습니다.
- **C. 발표 데모 시나리오**: 5분 안에 보여줄 순서입니다.

---

## A. 계산 규칙 시나리오

공통 조건: 반올림 단위 100원, 결제자는 A (S5만 예외).

| # | 상황 | 입력 | 기대 결과 |
| --- | --- | --- | --- |
| S1 | 기본 N빵 | 4명 모두 참석·음주·보통, 고기 80,000 + 술 20,000 | 모두 **25,000원** |
| S2 | 술 안 마신 사람 | S1에서 C·D가 술을 안 마심 | A·B **30,000원**, C·D **20,000원** (술 20,000은 A·B만 10,000씩) |
| S3 | 먹은 양 차이 | 고기 80,000, B 많이(1.5) · C 적게(0.5) · A·D 보통 | A **20,000** · B **30,000** · C **10,000** · D **20,000** |
| S4 | 일찍 간 사람 | 1차 고기 80,000 4명 / 2차 맥주 30,000 A·B만 | A·B **35,000원**, C·D **20,000원** (2차 0원) |
| S5 | 결제자가 다름 | S4와 같고 2차는 B가 결제 | 송금 **B → A 5,000원** 한 줄 (20,000과 15,000 상계) |
| S6 | 나누어떨어지지 않음 | 3명, 안주 10,000 "다같이" | B·C **3,400원**씩 송금, 남는 133원은 결제자 몫 |
| S7 | 혼자 시킨 메뉴 | 3명, 피자 30,000 + C 혼자 콜라 3,000 | A·B **10,000**, C **13,000** |
| S8 | 입력 실수 | 결제자 미선택, 아무도 술 안 마셨는데 "술" 항목 있음 | 경고 2개 표시, 술값은 참석자 균등으로 나눔, 송금 목록 없음 |

### 검산 메모

- S3: 비율 합계 = 1 + 1.5 + 0.5 + 1 = 4 → 80,000 ÷ 4 = 20,000이 비율 1의 몫.
- S5: 1차에서 B는 A에게 20,000, 2차에서 A는 B에게 15,000을 줘야 하므로 차액 5,000만 B → A.
- S6: 10,000 ÷ 3 = 3,333.3… → 100원 단위로 올려 3,400. 결제자 A는 본인 몫을 반올림하지 않음.

## B. 멀티 에이전트 시나리오

Agent 구성 (README 참고)

| Agent | 역할 | 필수 여부 |
| --- | --- | --- |
| Receipt Agent | 영수증 사진에서 메뉴·금액 추출 | 필수 |
| Situation Agent | 문장에서 참석·음주·먹은 양 추출 | 필수 |
| Classifier Agent | 메뉴를 먹은 양 / 술 / 다같이 / 한 사람으로 분류 | 필수 |
| `computeSplit()` | 결정적 계산 (LLM 없음) | 필수 |
| Explainer Agent | 사람별 "왜 이 금액" 설명 | 선택 |

### B-1. 정상

| # | 사용자 입력 | 흐름 | 기대 결과 |
| --- | --- | --- | --- |
| N1 | 영수증 1장 + "4명, 다 마셨어" | Receipt ∥ Situation → Classifier → 계산 → Explainer | S1과 같은 결과, 설명 포함 |
| N2 | 영수증 2장(1차·2차) + "C랑 D는 1차만 있다 갔고 C는 술 안 마셨어" | 영수증마다 Receipt 병렬 실행 → 차수별 참석 반영 | 2차 비용 C·D 0원, C 술값 0원 |
| N3 | "B가 엄청 먹었어, 콜라는 C 거야" | Situation이 B=많이, Classifier가 콜라=한 사람(C) | S3·S7 규칙이 적용된 결과 |

### B-2. 정보 부족 (추측하지 않고 되묻기)

| # | 상황 | 기대 동작 |
| --- | --- | --- |
| I1 | 누가 결제했는지 말이 없음 | "누가 결제했나요?" 질문, 계산 보류 |
| I2 | "콜라는 누가 시켰는지 모르겠어" | 해당 항목만 "다같이"로 둘지 사용자에게 선택지 제시 |
| I3 | 문장에 없는 이름이 등장 ("E도 잠깐 왔어") | 인원에 추가할지 확인 후 진행 |

### B-3. 부분 실패 (가능한 범위에서 계속)

| # | 상황 | 기대 동작 |
| --- | --- | --- |
| P1 | Explainer Agent 실패 (선택) | 정산 결과는 그대로 보여주고 "설명을 만들지 못했어요" 표시 |
| P2 | Receipt Agent 시간 초과 1회 | 1회 재시도 후 성공, Trace에 재시도 기록 |
| P3 | OpenAI 연속 실패 | Gemini로 전환, 같은 출력 계약으로 다시 검증, Trace에 사용 Provider 기록 |
| P4 | 영수증 한 줄이 흐려서 금액 인식 실패 | 그 줄만 "확인 필요"로 표시, 나머지 줄은 계속 처리 |

### B-4. 전체 실패 (안전하게 중단)

| # | 상황 | 기대 동작 |
| --- | --- | --- |
| F1 | 추출한 메뉴 금액 합계 ≠ 영수증 총액 | 계약 위반으로 계산 중단, 차이 금액과 함께 사용자에게 수정 요청 |
| F2 | Receipt Agent가 모든 Provider에서 실패 (필수) | 계산하지 않고 "영수증 금액을 직접 입력해 주세요"로 전환 |
| F3 | Classifier가 허용되지 않은 분류값(예: "디저트") 반환 | 계약 검증 실패 → 1회 재생성 → 또 실패하면 사용자에게 분류 요청 |
| F4 | LLM이 계산 결과 숫자를 바꿔서 설명 | 설명 속 금액이 `computeSplit()` 결과와 다르면 설명 폐기 (P1처럼 처리) |

### B-5. 승인과 거부 (Human-in-the-loop)

| # | 상황 | 기대 동작 |
| --- | --- | --- |
| A1 | 분류 결과 확인 화면에서 사용자가 **승인** | 계산 확정, 단톡방 문구 생성 |
| A2 | 사용자가 **거부**하고 "치킨은 다같이야"라고 수정 | 해당 항목만 다시 분류, 나머지 결과 유지 후 재계산 |
| A3 | 단톡방 문구 **발송 거부** | 아무것도 보내지 않음, 결과만 화면에 유지 |
| A4 | 같은 영수증을 두 번 업로드 | 멱등성 검사로 중복 차수 생성 막고 "이미 등록된 영수증" 안내 |

## C. 발표 데모 시나리오 (5분)

하나의 모임 이야기로 이어서 보여줍니다.

> 금요일 팀 회식. 5명이 1차 삼겹살집에 갔고, 서준과 하은은 술을 안 마셨고, 도윤은 많이 먹었고, 지영은 조금 먹었다. 하은은 사이다를 따로 시켰다. 서준과 하은은 1차만 있다 갔고, 나머지 셋은 2차 호프까지 갔다. 1차는 민수, 2차는 지영이 결제했다.

| 순서 | 보여줄 것 | 강조할 개념 |
| --- | --- | --- |
| 1 | 영수증 2장과 위 문장을 입력 | Parallel (Receipt ∥ Situation) |
| 2 | 결제자 누락 상태로 먼저 실행 → "누가 결제했나요?" | 정보 부족 시 되묻기 |
| 3 | 분류 확인 화면에서 "냉면은 다같이"로 수정 후 승인 | Human-in-the-loop |
| 4 | 결과: 송금 5줄, 도윤 → 지영 14,400원 등 | 결정적 계산, 상계 |
| 5 | 서준 "왜 이 금액?" 열기 → 술값 0원, 2차 0원 확인 | 공정성, 설명 가능성 |
| 6 | Trace 화면: Agent별 실행 시간·Provider·재시도 | 관측 가능성 |

예시 모임은 `web/index.html`의 기본 예시와 같아서, 계산 결과를 화면에서 바로 확인할 수 있습니다.
